| NDK | 독자적 비밀 알고리즘이 없어 불필요한 C++ 이전은 하지 않음. 기존 라이브러리 .so는 모두 내용 검사. C++ 이전만으로 비밀 보호를 보장할 수 없음 |

해시 목록 서명과 APK 서명은 같은 외부 키를 사용합니다. 서로 독립된 두 비밀키에 의한 방어는 아니며, 그 개인키가 유출되면 두 서명 모두 위조할 수 있습니다.

## 3. 빌드와 자기 참조 처리

R8 완료 unsigned APK → 엔트리 내용 해시 → 패키지/버전 포함 목록 → 목록 RSA 서명 → 두 asset 추가 → zipalign → APK 서명 순서입니다.
목록 및 목록 서명 두 파일만 해시 대상에서 제외하며, 목록은 승인된 현재 인증서의 공개키로 검증합니다.
해시 기대값을 DEX에 다시 넣고 재빌드하는 과정이 없으므로 자기 참조가 없습니다. 정렬·서명 블록으로 변하는 ZIP 오프셋과 압축 바이트 대신 엔트리의 압축 해제된 내용을 검사합니다.
목록에 없는 파일 추가, 필요한 파일 삭제, 중복 엔트리도 거부합니다. 본 검증은 단일 직접 배포 APK를 대상으로 합니다.

## 4. 실제 APK 검사 10건

APK 서명은 Android SDK apksig로 검증하고, 내용 검사는 **앱과 동일한 PackageIntegrity.java**를 JVM에서 실행했습니다. 단순히 임의의 파일 해시를 비교한 시연이 아닙니다. 단, 최종 R8 DEX 실행 테스트와는 구분합니다.

| 실제 파일 | 예상/실제 결과 | 의미 |
|---|---|---|
| normal.apk | OK | 정상 최종 Release 통과 |
| dex-modified.apk | CONTENT_HASH | DEX의 실제 문자열 데이터를 바꾸고 DEX SHA-1/Adler32 헤더를 다시 계산, 승인 검증 키로 APK 재서명해도 내부 해시에서 차단 |
| resigned.apk | SIGNER | 내용 그대로 다른 인증서로 재서명한 유효 APK 차단 |
| native-modified.apk | CONTENT_HASH | .so 바이트 변조 + 승인 키 APK 재서명 차단 |
| resource-modified.apk | CONTENT_HASH | resources.arsc 변조 + 승인 키 APK 재서명 차단 |
| added-dex.apk | ENTRY_SET | 추가 DEX 삽입 차단 |
| removed-resource.apk | ENTRY_SET | 핵심 리소스 삭제 차단 |
| index-modified.apk | INDEX_SIGNATURE | 기대 해시 목록 변조 차단 |
| unsealed.apk | UNREADABLE | 보호 목록 없는 APK 차단 |
| signature-broken.apk | APK_SIGNATURE_INVALID | 최종 APK를 재서명 없이 변조하면 플랫폼 서명 검증에서 거부 |

변조 APK에 승인 키로 다시 APK 서명한 사례는 시험을 위해서만 수행했습니다. 해시 목록 서명은 재생성하지 않았으므로, APK 서명 검사와 내부 내용 검사를 구분해 시험할 수 있습니다.
변형 APK의 개별 SHA-256과 실제 결과는 apk-cases.json에 있습니다. 검증 샘플은 설치/배포용이 아닙니다.

## 7. 우회 가능성 및 남은 위험

1. 공격자가 앱 코드와 인증서 pin, 검사 호출부를 함께 패치하거나 검사 결과를 후킹하면 우회할 수 있습니다. 오프라인 클라이언트 내부에 신뢰 기준과 검사기가 함께 있기 때문입니다. 이번 시험은 패치 불가능성의 증명이 아닙니다.
2. 루팅 기기·변조 OS·동적 계측은 PackageManager·파일 읽기·검증 함수를 속일 수 있습니다. 검사 후 사용 사이의 루트 권한 변조도 완전히 막지 않습니다.
3. R8는 식별자 난독화와 최적화이며 문자열·모든 제어 흐름·알고리즘을 암호화하지 않습니다. 일부 앱 컴포넌트와 Room 클래스명은 정상 실행을 위해 유지됩니다. 디버거 검사도 우회 가능합니다.
4. 키 유출은 치명적입니다. 서명된 목록과 APK를 모두 다시 만들 수 있습니다. 키의 안전한 보관과 고객용 배포 파일 검증이 필요합니다.
5. 서버 없이 즉시 인증서 폐기, 강제 업데이트, 기기별 라이선스 통제, APK 복제 방지는 제공하지 않습니다.
6. 현재 메모 DB에는 앱 차원의 별도 암호화/생체 잠금을 추가하지 않았습니다. APK 보호와 저장된 메모의 기밀성은 별개입니다.
7. 오류 시 저장을 막으므로 미저장 Draft는 앱 프로세스가 살아 있는 동안에만 유지됩니다. 강제 종료·전원 차단 전에 화면의 내용을 복사해 보관해야 합니다. 검사 실패 시 DB를 삭제하거나 ‘복구’를 명목으로 초기화하지 않습니다.
8. 정상 OS에서는 설치된 APK가 불변이며 업데이트가 프로세스를 교체합니다. 전체 파일 검사는 변경 작업마다 IO 비용이 있으므로 저성능 기기에서 입력/저장 지연을 실측해야 합니다.
9. NDK로 이전할 고유 비밀 알고리즘이 현재 없으므로 C++를 추가하지 않았습니다. 추후 도입해도 네이티브 분석은 가능합니다.
10. 공식 운영 인증서 지정, 실제 난독화 APK 설치 실행, 기존 서명에서 전환/데이터 이전, 삼성 위젯·재부팅·IME·장시간 사용 검수는 남아 있습니다. 고객 배포 완료로 승인하지 않습니다.
